# AutoToken architecture refactor and verification plan

## Overview

This plan restructures the project from a large script-style application into clearer modules with stable boundaries, while preserving the existing CLI, HTTP API, Web UI behavior, persisted data, and operational flows. It also completes the project rename from `autoteam` to `autotoken` with compatibility shims for existing deployments.

The work must proceed in small, verified units. The current codebase contains high-risk external flows: OpenAI/Codex OAuth, Team membership mutation, temporary mail providers, CPA sync, GoPay, PayPal, proxy services, and local SQLite state. Refactors must be characterization-first for existing behavior and must not rely only on unit tests.

## Problem Frame

The project structure is currently hard to maintain because:

- `src/autotoken/api.py` is about 871 KB and mixes FastAPI routing, config management, background task scheduling, task persistence, account APIs, PayPal orchestration, logs, startup/shutdown hooks, and static asset serving.
- `src/autotoken/manager.py` is about 255 KB and mixes CLI routing, account rotation, registration, OAuth follow-up, reconcile, cleanup, CPA sync triggers, and interactive flows.
- Payment and binding executors share helper functions through concrete module imports instead of a neutral service layer.
- Basic utilities such as redaction, JSON file I/O, task snapshot compaction, env compatibility, and normalization are duplicated or embedded in large business modules.
- The rename from AutoTeam/autoteam to AutoToken/autotoken touches package names, CLI names, docs, config keys, localStorage keys, database file names, build scripts, and compatibility requirements.

## Requirements Trace

- R1. Rename the project comprehensively from `autoteam` to `autotoken`, preserving compatibility where removing old names would break existing users.
- R2. Refactor by module boundaries without changing externally visible behavior.
- R3. Remove or consolidate duplicated helper code into shared modules with low-level dependencies only.
- R4. Reduce risk in large modules by extracting cohesive services before moving route handlers or command handlers.
- R5. Improve robustness through defensive compatibility, typed/pure helper modules, and focused regression tests.
- R6. Verify changes with automated tests plus real task testing for all major functions after implementation.
- R7. Do not run destructive, paid, account-mutating, or ToS-sensitive real tasks without explicit user-provided credentials, test targets, and approval.

## Scope Boundaries

- Do not redesign product behavior or change API/CLI contracts unless required for the rename and documented as compatible.
- Do not remove legacy `autoteam` import/CLI/env support until a separate deprecation plan exists.
- Do not perform real OpenAI account creation, Team kicks, GoPay/PayPal payment flows, or CPA mutations without explicit approval and test credentials.
- Do not rewrite the frontend design in this plan; only update naming and API compatibility unless a later unit targets frontend architecture.

## Context & Research

### Relevant Code and Patterns

- `docs/architecture.md` defines the account state machine, rotation flow, sync model, and core modules.
- `src/autotoken/api.py` currently owns too many architectural layers and should become an app composition layer plus route registration surface.
- `src/autotoken/manager.py` currently owns CLI commands and business workflows; command parsing should be separated from services.
- Existing persistence is centered on `src/autotoken/sqlite_store.py` and JSON compatibility files.
- Existing tests are under `tests/unit/` and already cover accounts, API status, bind tasks, mail providers, OAuth phone pool, reconcile, trade, and related units.

### Current Worktree Note

Some rename and initial extraction work already exists in the worktree:

- `src/autoteam` has been moved toward `src/autotoken`.
- A compatibility `src/autoteam/` package has been introduced.
- `pyproject.toml`, scripts, docs, web localStorage keys, and tests have partial `autotoken` updates.
- New low-level helpers have started under `src/autotoken/core/`.

Before further implementation, Unit 1 must stabilize and review this existing diff.

## Key Technical Decisions

- Use layered dependencies:
  - `core/`: pure helpers and compatibility utilities, no business module imports.
  - `services/`: account, task, OAuth, payment, sync orchestration.
  - `api/` or route modules: FastAPI request/response adapters only.
  - CLI module: argument parsing and command dispatch only.
- Keep old names as compatibility aliases:
  - `autoteam` package imports should route to `autotoken`.
  - Old `autoteam` CLI command may continue as alias while `autotoken` is canonical.
  - Old `AUTOTEAM_*` env vars should map to `AUTOTOKEN_*` where equivalent.
  - Existing `data/autoteam.sqlite3` should remain readable if no new database exists.
- Extract pure utilities first, then task runtime, then route groups, then CLI workflows.
- Use characterization tests before moving behavior out of large modules.
- Treat real task testing as a gated verification phase, not a default automated step.

## Real Task Verification Matrix

Real task verification must be run after code-level tests pass. These tests require explicit credentials and approval because they can mutate accounts, teams, CPA data, or payment/billing state.

### Always-run local verification

- Import smoke: import all major modules.
- CLI smoke: `autotoken --help`, `autoteam --help`, and non-mutating status/help commands.
- API smoke: start local API on a test port, call `/api/status`, `/api/tasks`, config status, and static Web UI.
- Unit suite: all tests under `tests/unit/`.
- Lint scope: new modules must pass ruff; legacy modules should be improved incrementally without blocking on unrelated historical findings.
- Web build: `npm run build` under `web/`.

### Real non-payment task verification

Requires configured `.env`, test OpenAI/ChatGPT workspace, test mail provider, and CPA test endpoint if CPA is enabled.

- Setup wizard/config save with each configured mail provider.
- Temporary mail create/search/delete using the configured test provider.
- Manual OAuth callback parsing with a known safe callback URL.
- CPA export/import against a test CPA endpoint or disposable namespace.
- Reconcile dry-run against a test workspace.
- Quota check against disposable test auth files.

### Real mutating task verification

Requires explicit approval per run.

- Team member sync and reconcile with a disposable workspace.
- Rotate/check/fill/cleanup on a test workspace with known accounts.
- Auto registration only with disposable accounts and clear stop conditions.
- Account delete/kick only against accounts approved for removal.

### Real payment/binding verification

Requires explicit approval, test card/wallet/PayPal assets, budget limits, and rollback/cleanup instructions.

- GoPay bind task using a disposable account and test wallet/phone source.
- PayPal task using a disposable account and approved test payment method.
- Failure-path verification for proxy failure, OTP timeout, payment not approved, and token invalidated cases.

### Real Task Go/No-Go Checklist

Use this checklist before running any real task that can mutate external state. Do not treat a local green test suite as approval to run these tasks.

**Required before any real run:**
- Explicit user approval for the exact command or UI workflow.
- Disposable target accounts/workspace/team members listed by email or account id.
- CPA/test provider endpoint or namespace identified when CPA sync/import/export is involved.
- Budget limit stated for any paid payment, wallet, phone, SMS, or provider action.
- Rollback/cleanup owner and expected cleanup action documented before start.

**Go conditions:**
- Local completion audit is still current: full unit suite, full-project ruff, Web build, package build, CLI smoke, and API smoke pass.
- `.env` points to test resources, not production assets, unless production verification is explicitly approved.
- The operation has a bounded scope: account count, task count, payment count, timeout, and retry limit are known.
- A progress/result capture location is known (`/api/tasks`, logs, CPA namespace, or exported task result).

**No-Go conditions:**
- Missing or ambiguous account/payment ownership.
- No explicit budget limit for paid flows.
- Any target looks like a real user/customer/production asset and has not been explicitly approved.
- Rollback cannot be performed or verified.
- The requested task would bypass the documented safety boundaries in R7.

**Evidence to capture after each run:**
- Exact command or endpoint invoked, with secrets redacted.
- Task id and final task status/result payload.
- Accounts/members/payment assets touched.
- Cleanup performed and post-cleanup verification.
- Any external error payloads needed for follow-up debugging.

## System-Wide Impact

- **Interaction graph:** FastAPI routes call task runtime and services; services call accounts, auth, mail, CPA, payment executors, and SQLite.
- **Error propagation:** Route handlers should translate service exceptions to HTTP errors; background tasks should store structured task results and progress events.
- **State lifecycle risks:** Account mutations, auth-file writes, SQLite snapshots, CPA sync, payment state, and task cancellation must remain idempotent where possible.
- **API surface parity:** CLI and HTTP task routes must keep equivalent behavior for rotate, check, fill, cleanup, reconcile, OAuth, and sync.
- **Integration coverage:** Unit tests alone are insufficient for OAuth, browser automation, payment flows, provider APIs, and CPA sync.
- **Unchanged invariants:** Existing account status names, API route paths, task JSON keys, and auth-file formats remain stable unless explicitly versioned.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Rename breaks existing deployments | Keep `autoteam` package/CLI/env/db compatibility during migration |
| Refactor changes external behavior silently | Add characterization tests before moving workflow code |
| Payment/OAuth real tasks cause side effects | Gate all mutating real tests behind explicit approval, disposable assets, and budget limits |
| `api.py` extraction creates circular imports | Extract pure `core` and service modules first; verify import smoke after each unit |
| Legacy lint failures obscure new issues | Require new modules to pass ruff; handle legacy violations in targeted cleanup units |
| Generated assets or docs drift from runtime | Separate runtime rename validation from docs/generated asset cleanup |

## Open Questions

### Resolved During Planning

- Should `autoteam` compatibility be removed immediately? No. Keep compatibility to avoid breaking existing scripts and deployments.
- Should real payment/account-mutating tests be automatic? No. They require explicit credentials and approval.

### Resolved During Implementation

- Exact final route module layout: FastAPI app composition lives in `src/autotoken/interfaces/api.py`; domain route groups live under `src/autotoken/api_routes/*`; the remaining GoPay bind and PayPal task routes stay at the API interface boundary as payment-orchestration compatibility surfaces.
- Whether `manager.py` becomes a thin compatibility wrapper or remains the CLI module: CLI parser/startup/dispatch now live in `src/autotoken/interfaces/cli.py`; `src/autotoken/interfaces/manager.py` keeps the historical `main()` entry point plus public `cmd_*` workflow functions for compatibility while delegating decision logic to services. Root `src/autotoken/manager.py` and `src/autotoken/cli.py` are thin compatibility wrappers.
- Which historical docs should keep AutoTeam references as upstream history: runtime/package/docs cleanup now uses `autotoken` as the canonical name; `autoteam` references are limited to explicit compatibility surfaces, historical migration context, or tests that guard the compatibility contract.
